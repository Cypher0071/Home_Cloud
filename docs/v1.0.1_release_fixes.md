Audit of public `origin/main` at `1c9b767d71ea445997483049b819c72768681d97`, which is git tag `v1.0.0` and the GitHub release "Home Cloud v1.0.0 — Official Launch".

## Subdomain sessions — read this before touching cookies

The audit finding is **not** "a logged-in operator must sign in again on every subdomain."

What the product does today:

- Login sets a host-only cookie. `agent/routes/auth.js` sets `token` with `httpOnly` and `sameSite: 'lax'`. It does not set a `Domain` attribute.
- The browser stores that cookie for the host that served login (`dash.example.com`, or the LAN host). It sends the cookie only when the request **target** is that host.
- `grafana.example.com`, `jellyfin.example.com`, and the other ingress names are separate apps. They never receive this cookie. Home Cloud does not log the operator into those apps.

What the operator experience is:

- Open `dash.example.com`, log in once, and the dashboard stays logged in across tabs and reloads of that same host.
- Open `grafana.example.com` and you are in Grafana. Grafana has its own login, or none. Home Cloud does not, and should not, reuse the dashboard JWT there.

What the actual bug is:

- `dash.example.com` and `grafana.example.com` are different origins and the **same site** (same registrable domain).
- `SameSite=Lax` still sends the dashboard cookie on a same-site request whose target is `dash.example.com`.
- A page already loaded on a sibling hostname can therefore ask the browser to call the dashboard. The browser attaches the dashboard cookie. The agent accepts any request that carries a valid cookie.
- Neither WebSocket checks `Origin` (`agent/sockets/terminal.js`, `agent/sockets/containerExec.js`). Authenticated HTTP routes do not either.
- JSON `fetch` from that page is blocked by CORS, because only `/api/ping` and `/api/health` set `Access-Control-Allow-Origin`. These are not blocked:
  - a WebSocket to `wss://dash.example.com/terminal` or `/ws/docker/exec`
  - a form `POST` (no preflight) to a route that takes its input from the URL, such as `POST /api/docker/containers/:id/stop`
  - a top-level navigation that carries the Lax cookie

So a compromised or simply malicious page on a hostname the operator exposed can open the host shell and hit state-changing dashboard routes while the operator is logged in. The operator does not see a second login prompt. That is the bug.

Required fix (P0-2 below): allowlist the dashboard origin on cookie-authenticated HTTP and on both WebSocket upgrades. Leave the cookie host-only.

Do not do this:

- Do not set `Domain=.example.com` on the session cookie. Every exposed app would then receive the host-admin JWT.
- Do not add a Home Cloud login wall in front of Grafana, Jellyfin, or other ingress hostnames as the fix for this bug.
- Do not treat "stay logged in on the dashboard" as something to remove. That behavior stays.

One login for every exposed app is a different feature (Cloudflare Access, forward auth, or an oauth2 proxy per hostname). It is not this cookie, and it is not part of this list unless it is designed so those apps never see the dashboard JWT.

## P0 — do these first

### P0-1. Make the vulnerability channel real

`SECURITY.md` tells reporters to open a GitHub private advisory or email `security@homecloud.local`. Private vulnerability reporting is disabled on `Cypher0071/Home_Cloud`. `.local` is not a public mail domain, so that mailbox cannot receive mail. `.github/ISSUE_TEMPLATE/config.yml` links the same advisory URL and also links GitHub Discussions, which is disabled (HTTP 404).

Changes:

- Enable private vulnerability reporting on the GitHub repo.
- Remove `security@homecloud.local` from `SECURITY.md`.
- Point `SECURITY.md` and `.github/ISSUE_TEMPLATE/config.yml` only at the advisory URL.
- Enable Discussions, or delete that contact link.
- Enable Dependabot alerts and secret scanning. Turn on secret-scanning push protection.
- Protect `main` (pull request required, or at least no direct force-push) so a bad commit cannot replace the release branch silently.

Done when a logged-out visitor can start a private advisory, the `.local` address is gone, and the issue template has no 404 links.

### P0-2. Bind the dashboard session to the dashboard origin

Files: `agent/routes/auth.js`, `agent/middleware/auth.js`, `agent/sockets/terminal.js`, `agent/sockets/containerExec.js`.

Changes:

- Keep the cookie host-only. Do not add a parent `Domain`.
- On every cookie-authenticated HTTP request, require an `Origin` (or, when `Origin` is absent, a same-origin `Referer`) that matches the host the dashboard is being served from. Reject missing or foreign origins on state-changing methods.
- On both WebSocket upgrades, require `Origin` to be that same dashboard origin. Close the socket otherwise.
- Allow the LAN origin and the `dash.$CF_DOMAIN` origin when both are actually in use. Do not allow every host under `$CF_DOMAIN`.
- Add a regression test: a same-site foreign `Origin` is rejected for the terminal socket and for `POST /api/docker/containers/:id/stop`. A same-origin dashboard request still works.

Done when a sibling hostname cannot open `/terminal` or call a no-body `POST` with the operator's cookie, and a normal dashboard session still survives reload.

### P0-3. Stop trusting client-supplied client IPs

File: `agent/routes/auth.js` (`getClientIp`).

The login lockout prefers `CF-Connecting-IP`, then `X-Forwarded-For`, from any connection. A client that can reach port 3000 directly can rotate those headers and get a new 5-attempt window. `SECURITY.md` also calls the lockout exponential backoff. The code is a fixed window: 5 failures in 60 seconds, then 5 minutes.

Changes:

- Rate-limit on the socket address.
- Honor `CF-Connecting-IP` only when the peer is the local `cloudflared` process.
- Cap the in-memory attempt map.
- Either implement exponential backoff or change `SECURITY.md` to describe the fixed window.
- Stop returning `remainingAttempts` to the client, or keep it only if the tests require it and the window can no longer be reset by a header.

Done when two requests from the same TCP peer share one counter even if their forwarding headers differ.

### P0-4. Make logout match the security policy

Files: `agent/routes/auth.js`, `SECURITY.md`.

`SECURITY.md` says logout increments `sessionEpoch` and kills existing JWTs on HTTP and WebSocket. `POST /api/auth/logout` only clears the cookie. The JWT stays valid for 7 days. `res.clearCookie('token')` also omits `httpOnly`, `secure`, and `sameSite`, so a `Secure` cookie set through the tunnel may not clear. `POST /api/auth/logout-all` and the password change do bump the epoch.

Changes:

- Bump `sessionEpoch` on logout, or document a separate "this browser only" logout and make `SECURITY.md` match the code. Pick one behavior and test it.
- Pass the same cookie flags into `clearCookie` that `res.cookie` used.

Done when a logged-out token is rejected by `/api/auth/me` and by both sockets, including a copy of the cookie that never got cleared.

### P0-5. Refuse placeholder secrets at startup

Files: `agent/index.js` or `agent/config.js`, `agent/.env.example`, `README.md`.

`agent/.env.example` ships `PASSWORD=change-me` and `JWT_SECRET=generate-a-long-random-string`. Login rejects only an empty password (`configuredPassword.length > 0`). A manual `cp agent/.env.example agent/.env` is a public admin password and a public signing key on a process that can open a host shell. `setup.sh` does replace both before it starts the service. The agent itself does not.

Changes:

- Refuse to listen when `PASSWORD` or `JWT_SECRET` is missing, shorter than a stated minimum (`PASSWORD` minimum 8, matching the settings API), or equal to those two placeholders.
- Keep the installer behavior that rewrites both.
- Say this in the README next to the `cp agent/.env.example` step.

Done when starting the agent against an unchanged example env exits before it binds port 3000, and a generated installer env still boots.

## P1 — code fixes for 1.0.1

### P1-1. Close the wallpaper path escape

Files: `agent/services/preferences.js` (`getWallpaperPath`), `agent/routes/settings.js` (`PUT /api/settings/preferences`).

The upload handler writes `wallpaper.${ext}` with `path.join` and an allowlisted MIME map. The read path concatenates `personalization.customWallpaperExt` onto `WALLPAPER_FILE_PREFIX` and calls `existsSync`. `PUT /api/settings/preferences` stores `personalization` with no key allowlist, so that extension string can contain `..`. File-explorer Safe Server Mode does not apply to this route. The response is also `Cache-Control: public`.

Changes:

- Allow only `.png`, `.jpg`, `.jpeg`, `.webp`, `.gif`.
- Resolve the file with `path.resolve` under `PREFERENCES_DIR` and reject anything outside it.
- Ignore `customWallpaperExt` from the preferences body. Only the upload handler may set it.
- Do not mark authenticated wallpaper bytes `Cache-Control: public`.

Done when a preferences write cannot change the wallpaper path, and a normal uploaded image still renders.

### P1-2. Stop serving user files as active content on the dashboard origin

File: `agent/routes/file.js` (`GET /view`).

The storage jail on this route is real. The bytes are still sent `Content-Disposition: inline` with a type taken from the extension, including HTML and SVG. There is no `X-Content-Type-Options: nosniff` and no CSP. A top-level open of that URL runs in the dashboard origin.

Changes:

- Send `Content-Disposition: attachment` for everything except a small image allowlist, or serve user files from a different host.
- Set `X-Content-Type-Options: nosniff` on this response.
- Never use `text/html` or `image/svg+xml` for an inline same-origin response.

Done when opening an `.html` file from the file API downloads it or shows it as text, and does not execute it on the dashboard origin.

### P1-3. Encode passwords before writing `.env`

File: `agent/routes/settings.js` (password update).

The rewrite drops the new password into `PASSWORD=...` with a regex. Dotenv treats `#` as a comment and a newline as a new record. The temp-file rename is atomic and mode `0600`. The value is not safely encoded, and two writers can still lose an update.

Changes:

- Reject CR, LF, and NUL in the new password.
- Write a quoted value, parse the result with the same dotenv parser the agent uses, and refuse the write if `PASSWORD` does not round-trip or if any other key changed.
- Keep mode `0600`.

Done when a password containing `#` still matches after a process restart, and `JWT_SECRET` in the file is unchanged.

### P1-4. Keep agent secrets out of the host shell

File: `agent/sockets/terminal.js`.

`pty.spawn` copies `process.env`, which includes `PASSWORD`, `JWT_SECRET`, and `GITHUB_TOKEN` when those are set. The session also replays scrollback to a later attach.

Changes:

- Pass a minimal environment: `PATH`, `HOME`, `USER`, `SHELL`, `TERM`, `LANG`, `LC_ALL`.
- Delete `PASSWORD`, `JWT_SECRET`, `GITHUB_TOKEN`, and any other `*_SECRET` / `*_TOKEN` before spawn.

Done when a new terminal's `env` output does not contain those keys. Existing operator environment variables from the service unit that the shell legitimately needs (`PATH`, `HOME`) still work.

### P1-5. Pin the update target to a real release tag

Files: `agent/routes/settings.js`, `agent/services/updateManager.js`.

`git fetch` stays on `origin`, and commands are `spawn` argument arrays. `targetTag` from the JSON body is still passed to `git checkout`. If it is omitted, the code checks out the cached tag or runs `git pull origin main`, then `pnpm install` (lifecycle scripts run) and restarts the service.

Changes:

- Accept only a semver tag that `git ls-remote` advertised from `origin`.
- Reject a value that starts with `-`.
- Keep `spawn` without a shell.
- Default the no-argument apply path to the latest GitHub release tag, not floating `main`.

Done when an apply request cannot check out an arbitrary ref, and a normal update to the next release tag still runs.

### P1-7. Stop the installer from piping unpinned third-party scripts

File: `setup.sh`.

The script uses `set -euo pipefail`, quotes flag values, replaces `change-me`, generates a JWT from `/dev/urandom`, and substitutes every `{{...}}` placeholder in `home-cloud.service.template`. These URLs are still fetched and executed with no checksum. Some run as root:

- `https://deb.nodesource.com/setup_24.x` piped to bash (`setup.sh` Node install)
- `https://get.pnpm.io/install.sh` with `PNPM_VERSION=latest`, plus `npm install -g pnpm@latest`
- `https://get.docker.com` piped to `sh`
- `cloudflared` from GitHub `releases/latest` (deb, rpm, and raw binary)

Other installer gaps:

- Default branch is floating `main` (`HOME_CLOUD_BRANCH`, default `main`). A 1.0.x installer should clone and check out tag `v1.0.1` (or whatever this release is).
- Node check accepts any major `>= 20`. pnpm 11.5.1 needs `>= 22.13`. Astro 7 needs `>= 22.12`. An existing Node 20 is left in place and then fails install. CI already showed this on the Node 20 job.
- `pnpm install` is not `pnpm install --frozen-lockfile`.
- The generated admin password is printed and is passed to `node -e` in argv, so it shows up in `ps`. Write it only into `agent/.env` (mode `0600`).
- `--password` has no minimum length. The settings API requires 8 characters.
- `sed` renders the systemd unit. A newline, `|`, or `&` in `--dir` can abort or corrupt `/etc/systemd/system/home-cloud.service`. Reject those characters.
- If the script runs as root with no `SUDO_USER`, the unit's `User=` becomes root. Refuse that unless an admin user is explicit.
- `apt-get` / `dnf` / `pacman` failures and `git checkout` failures are swallowed with `|| true`.

Changes:

- Pin Node, pnpm, Docker, and cloudflared. Verify published checksums before install. For Docker, prefer "already installed" over `get.docker.com`.
- Install pnpm with `corepack prepare pnpm@<pinned> --activate`, the same version CI uses.
- Default the clone and the raw URL in the README to the release tag.
- Require Node `>= 22.13`.
- Use `pnpm install --frozen-lockfile`.
- Do not echo the password. Do not put it in argv.
- Enforce the 8-character password minimum.
- Reject CR, LF, `|`, and `&` in `--dir`.
- Refuse `User=root` unless requested.
- Remove the `|| true` on package install and `git checkout`.

Done when `bash -n setup.sh`, `./setup.sh --help`, and `./setup.sh --dry-run` still pass in CI, and a read of the script shows no `curl | bash` and no `releases/latest`.

### P1-8. Unset `CF_DOMAIN` must mean unset

Files: `agent/config.js`, `agent/services/ingress.js`, `agent/.env.example`, `README.md`.

`CF_DOMAIN` falls back to `home-cloud.live` when the env var is missing. Ingress then writes hostnames on a domain the operator may not control. The README calls the variable optional and does not mention that default.

Changes:

- Treat a missing `CF_DOMAIN` as "ingress autowiring off".
- Do not write `*.home-cloud.live` into the user's `config.yml` unless they set that domain.
- Document the default behavior in the README and in `.env.example`.

Done when a fresh env with no `CF_DOMAIN` cannot modify `~/.cloudflared/config.yml`.
